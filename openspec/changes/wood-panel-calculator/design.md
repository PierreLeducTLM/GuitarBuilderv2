# Design

## Context

What earlier changes left for this one:
- `/wood-properties` is a section placeholder behind the shell's sign-in gate;
- `public.is_admin()` and `public.set_updated_at()` exist;
- `DialogProvider` (confirm), `useToast` (four kinds, 3 s default) and the shared number and date formats exist;
- `tap-tone-dialog`, applied first, provides:
  - `TapToneDialog` (`open`, `label`, `currentValue`, `savedRecord`, `onConfirm(frequency, record)`, `onCancel`);
  - `public.spectrum_record_is_valid(jsonb)`;
  - the `SpectrumRecord` type in `@gb/db`.

The requirements are `openspec/specs/wood-panel-properties/spec.md` with this change's delta; the scope and deferrals are in proposal.md. The legacy audit (`docs/rewrite/legacy-findings/wood-panels-simulator.md`) lists the defects not to repeat:
- the `L^4/42` cross-grain formula;
- `updated_at` never moving;
- names checked trimmed but saved untrimmed;
- fetch errors shown as an empty library;
- "Load Default Panels" copying client-side, so a double click duplicated panels;
- nullable owners and no server-side value checks;
- admin write access to every panel;
- unsanitized PDF file names with a UTC date;
- Helvetica unable to render "ρ" and "³";
- hard-coded English.

Two checks were run before writing this design:
- **The formulas against the dataset.** The spec's formulas were applied to `docs/reference-data/measured-elasticity-dataset.json`. Density, E_L, E_C and G_LC match all 28 plates at the dataset's precision. The dataset's `target_thickness_mm` and `mass_target_g` columns do not match: with the spec's 500 × 380 mm plate and f = 75, they are 1–3% lower for the tops and about 28% lower for the backs. The implied stiffness parameter is 73.0–74.2 for the tops and about 54 for the backs, so the dataset used target settings it does not record. The spec's own worked example (2.77 mm and 157.5 g for plate 1) is what the formulas give.
- **The same formulas as Postgres generated columns,** in a throwaway Postgres 16 cluster. They reproduced 395.9 kg/m³, 11.84, 0.82 and 0.91 GPa, 2.77 mm and 157.5 g. The check also confirmed that Postgres orders `NaN` above every number, so `x > 0` alone accepts `NaN`.

## Goals / Non-Goals

**Goals:**
- Every `wood-panel-properties` requirement except "Analyse" and the PDF's AI section (deferred to `knowledge-assistant`), in English and French and in both themes.
- Every access and data rule enforced in Postgres, with pgTAP tests.
- One TypeScript implementation of the formulas for the page and the import. The stored snapshot is computed by the database, and both implementations are tested against the same worked examples.

**Non-Goals:**
- No reference-set curation UI and no template setting (`admin-console`).
- No link between panels and builds (owner question still open; see Open Questions).
- No "save as copy" and no unsaved-changes warning. The spec keeps the legacy behavior.

## Decisions

### 1. The `wood_panels` table

| Column | Definition |
|---|---|
| `id` | `uuid primary key default gen_random_uuid()` |
| `owner_id` | `uuid not null default auth.uid() references auth.users on delete cascade` |
| `name` | `text not null check (name ~ '\S')` |
| `sample_length_mm`, `sample_width_mm`, `sample_thickness_mm`, `sample_mass_g`, `freq_longitudinal_hz`, `freq_cross_grain_hz`, `freq_diagonal_hz`, `plate_length_mm`, `plate_width_mm` | `double precision not null check (x > 0 and x < 'Infinity')` |
| `stiffness_parameter` | the same, `default 75` |
| `e_long_gpa`, `e_cross_gpa`, `g_lc_gpa`, `target_thickness_mm`, `estimated_mass_g` | `double precision generated always as (public.wood_…(<the ten inputs>)) stored` |
| `spectra` | `jsonb not null default '{}' check (public.wood_panel_spectra_is_valid(spectra))` |
| `created_at`, `updated_at` | `timestamptz not null default now()`; `updated_at` is moved by the existing `set_updated_at()` trigger |

- An index on `(owner_id, created_at desc)` serves the library.
- **Why `< 'Infinity'`:** it rejects both infinity and `NaN`, which Postgres sorts above every number (see Context).
- **The client trims the name;** the check only refuses blank names.

**The results snapshot is generated by the database.**
- Five `immutable` SQL functions (`public.wood_e_long_gpa(...)` and so on, `set search_path = ''`) implement the spec's formulas from the ten inputs, and the generated columns call them.
- This meets Stored Results Snapshot ("results … at save time") by construction:
  - the snapshot is always the function of the stored inputs;
  - clients cannot write it, because generated columns accept no writes;
  - a panel imported later by `legacy-data-migration` gets corrected values without its own recalculation step.
- Alternative considered: the client sends the snapshot. Rejected because a modified client could store values that contradict the inputs, and the import would need its own copy of the math anyway.
- Cost: the formulas exist in SQL and in TypeScript (decision 4). Both are tested against the spec's examples and the same dataset plates.

**`estimated_mass_g` is never null** for panels saved or imported in v2, because it is generated. The UI still omits "Est. Mass" when it is null (Stored Results Snapshot scenario), so the type stays nullable for safety.

**Spectra:**
- `public.wood_panel_spectra_is_valid(jsonb)` requires an object whose keys are a subset of `longitudinal`, `crossGrain` and `diagonal`, each value passing `spectrum_record_is_valid`.
- The legacy keys (`freqLongitudinal`, …) are mapped by the import, as Wood Panel Spectrum Migration specifies.
- Spectra stay in the row, not in a side table. Three records are about 55 KB, and the library query never selects the column.

### 2. Access rules

**Row-level security on `wood_panels`, `to authenticated`:**
- select where `owner_id = auth.uid() or public.is_admin()`;
- insert with check `owner_id = auth.uid()`;
- update using and with check `owner_id = auth.uid()`;
- delete using `owner_id = auth.uid()`;
- `anon` gets no grant and no policy.

**Column grants** after `revoke all`:
- select on every column;
- insert and update only on `name`, the ten inputs and `spectra`.

So clients cannot set the owner, the timestamps or the snapshot.

**The library query filters `owner_id = <the signed-in user>` explicitly,** because RLS alone would list everyone's panels for an administrator (Panel Ownership and Access).

### 3. Reference panels and "Load Default Panels"

**`default_wood_panels`** has the same name, inputs and generated snapshot as `wood_panels`, plus `id` and `created_at`. It has no owner and no spectra (Reference Panel Set).
- RLS lets every authenticated user select.
- Insert, update and delete are allowed only where `public.is_admin()`.
- Grants follow the same column pattern.
- `admin-console` adds the sync and delete UI on top. Until then, the set is filled by the import or by the operator in SQL.

**`public.load_default_wood_panels() returns integer`** (`SECURITY INVOKER`, `search_path = ''`, executable by `authenticated` only). In one transaction it:
1. takes `pg_advisory_xact_lock` on a key derived from `auth.uid()`;
2. returns `null` when the caller already owns a panel;
3. otherwise inserts a copy of every reference panel (name and inputs) and returns how many it copied.

- **Copying at most once:** the lock serializes two tabs or a double click, and the second call sees the copies and returns `null`. This meets the delta's "Two tabs at once".
- **What the client does with the result:**
  - `0`: shows "No default panels are available yet";
  - any other number, or `null`: refreshes the library.
- Running as invoker means the normal insert policy and grants apply. The function can only ever create panels owned by the caller.
- Alternative considered: copying from the browser (legacy). Rejected because of the double-click duplication and the race between the count and the inserts.

### 4. The math: `@gb/dsp` `wood/properties.ts`

`woodProperties(inputs)` returns `{ density, eLong, eCross, gLc, targetThickness, estimatedMass }`:
- inputs in the spec's units: mm, g, Hz and the dimensionless stiffness parameter;
- outputs in kg/m³, GPa, mm and g;
- computed in SI internally, exactly as the spec writes the formulas, with E_C using the sample width.

**Tests:**
- The spec's worked examples: defaults 425.2 kg/m³ and 8.86 GPa; 357.1 kg/m³; the unit cube; the reference spruce panel (395.9, 11.84, 0.82, 0.91, 2.77 mm, 157.5 g); the 226.5 g mass example; the 2.7738 → "2.77" formatting.
- All 28 dataset plates for density (1 decimal) and E_L, E_C, G_LC (2 decimals).
- The dataset's target thickness and mass columns are **not** used as expected values, because they rest on unrecorded target settings (see Context). A comment in the test explains why.

The module lives in `@gb/dsp`, which `openspec/config.yaml` names as the package shared with the wood calculator. The legacy import can then use it outside the app.

### 5. Page structure and data flow

**`/wood-properties` is a Server Component.** It reads the library: `id, name, created_at, target_thickness_mm, estimated_mass_g`, with the owner filter, newest first.
- A failed query renders "Failed to load wood panels" in the library area, with no empty state (delta: Library Load Failures).
- `loading.tsx` shows the page skeleton.
- The page passes the list to the client component `WoodCalculator`.

**Calculator state** (client):
- `inputs` holds ten strings exactly as typed; the defaults are "280", "70", "3.0", "25", "180", "90", "120", "500", "380" and "75";
- `spectra` holds records by field key;
- also `name`, `loadedId` and the dialog state.
- A pure `parseInputs` and `validateInputs` (`apps/web/src/lib/wood/`) give the numbers and the error keys. An empty or non-numeric entry counts as 0.
- `woodProperties` runs on every render while all inputs are valid. There is no calculate button and no debounce, because the math is microseconds.

**Inputs** are `<input type="number" step="0.1" inputMode="decimal">` in the `Field` frame, with each symbol and unit in the label.
- The browser parses its own locale's decimal separator and reports a non-numeric entry as empty, which the spec asks to treat as missing.
- Alternative considered: a text input with our own parser. Rejected: it would lose the 0.1 stepping the spec names, and the native control handles locale input.

**Writes** go through the browser Supabase client, followed by `router.refresh()` to reload the list:
- **Save:** insert `name.trim()`, the ten numbers and `spectra`, returning `id`.
- **Update:** update by `id` with `.select('id')`. Zero rows (deleted elsewhere, or not the owner) counts as a failure.
- **Delete:** delete by `id` with `.select('id')`, after the confirmation.
- **Load:** select the ten inputs and `spectra` by `id`. An error or no row gives "Failed to load wood panel" (delta).
- **Defaults:** `rpc('load_default_wood_panels')` (decision 3).

Buttons are disabled, and guarded by a ref, while their request runs, so a double click sends one request. Outcomes use the messages and toast kinds of Notifications.

**Loading a panel:**
- frequencies are rounded to one decimal;
- the other inputs are shown as stored;
- the stored spectra are restored and results recomputed.

The entry shows "Currently editing" and the "PDF" action. "Analyse" appears with `knowledge-assistant`. Clicking the loaded entry again deselects and resets.

### 6. Tap-tone fields

Next to each frequency input, an `IconButton` labelled "Detect frequency from recording" opens `TapToneDialog` with:
- the field's translated label ("Longitudinal Frequency (f_L)" and so on);
- `currentValue` set to the field's number when it is greater than 0;
- `savedRecord` set to the field's spectrum, if any.

`onConfirm` writes `round(f, 1)` into the field and stores the record under that field's key. Cancel changes nothing.

**Typing a frequency by hand keeps that field's spectrum,** because the spec keeps "the most recently accepted spectrum". Reopening then preselects the peak nearest the typed value, which the dialog's reopen rule already handles. (A legacy finding called this stale; the spec does not.) Reset and deselect discard unsaved spectra, as specified.

### 7. PDF report

**Library:** `pdf-lib` with `@pdf-lib/fontkit`, both MIT, loaded with a dynamic `import()` only when "PDF" is pressed. The fonts are embedded as subsets.
- Alternative considered: jsPDF. It is maintained and has built-in wrapping, but it embeds whole fonts and has a larger API surface. pdf-lib's surface is small and its output deterministic; it has had no release since 2021 and no open advisories. Wrapping is a 20-line helper using the font's measured widths.

**Fonts:** static Space Grotesk Regular and Bold (words) and JetBrains Mono Regular and Bold (numbers and symbols), as TTF files under `apps/web/public/fonts/pdf/` with `OFL.txt`.
- They are fetched only when generating.
- Space Grotesk has no Greek, so "ρ" is drawn in JetBrains Mono, consistent with mono for symbols and numbers.
- The `@fontsource-variable` packages the app already uses ship only subset WOFF2 variable files, which are unsuitable for PDF embedding.

**Building the report, in two parts:**
- **`reportContent(values, t, format)`** (pure) returns the ordered sections and lines:
  - the title;
  - the panel name: the name field, or the loaded panel's name;
  - "Generated on <local date and time>";
  - Input Parameters, then Calculated Results, with the specified precisions in the user's locale.

  Unit tests compare it to the PDF Report Contents scenarios.
- **`renderReport(content, fonts)`** lays it out: A4, 20 mm margins, headings, label/value rows, and new pages as needed. The "AI Analysis" page is added when an analysis is supplied, which `knowledge-assistant` will do.

**Colors** come from the light theme's tokens in `@gb/ui/tokens`, because paper is light.

**The file name** is the panel name with `/ \ : * ? " < > |` and control characters replaced by "-", then `_`, then the local `YYYY-MM-DD` (delta scenario).

**Flow:**
1. "Generating PDF report..." (info).
2. Build and download through an object URL.
3. "PDF downloaded successfully!", or "Failed to generate PDF. Please try again." if anything throws.

### 8. Layout and look

**Desktop (≥ 1024 px):**
- "Input Measurements" in the left column: four groups of fields, with the reset control in the panel header;
- "Calculated Results" in the right column, sticky;
- "Saved Wood Panels" below, across the full width.

**Phone:** the three areas stack in that order.

**Results:** an instrument readout.
- "Recommended Thickness" is the large amber mono figure.
- Density, the moduli and the mass are mono values on graticule rows.
- Units are dim.
- While invalid, the area shows "Please fix input errors to see results" instead.

**Library entries** are buttons in cards: name, date in `short` format, "Target thickness" and "Est. Mass" in mono, and the delete control. The loaded entry gets the amber ring and the "Currently editing" chip.

Existing tokens are enough. If one is added, it goes through the contrast test.

### 9. Text

Every string lives under `wood.*` in `en.json` and `fr.json`:
- labels with symbols and units;
- hints;
- the ten validation messages;
- empty and error states;
- all notifications;
- the delete dialog;
- the PDF headings and labels;
- the three capture labels.

The PDF uses the same catalogs. The French scenario strings ("Mesures d'entrée", "Enregistrer le panneau") are used as written.

### 10. Tests

**Unit tests:**
- `@gb/dsp` math (decision 4);
- parsing and validation: each message, empty and non-numeric as missing, the fix-clears-error scenario;
- `reportContent` against the PDF scenarios in English and French;
- the file-name function;
- a font check: every character the report can contain (both catalogs plus digits, "ρ", "³" and "–") has a glyph in the font that draws it.

**pgTAP:**
- `11_wood_panels_schema`: columns, checks (blank name, 0, negative, `NaN` and infinity refused), generated values for the reference spruce panel and two dataset plates, `updated_at` moving and `created_at` fixed, the spectra check, grants and function settings;
- `12_wood_panels_access`: owner CRUD; another user and anonymous get nothing; an administrator reads but cannot insert, update or delete; the snapshot, owner and timestamps are not writable; panels cascade with their user;
- `13_default_wood_panels`: everyone reads and only administrators write; `load_default_wood_panels` copies into an empty library, returns `null` for a non-empty one and `0` for an empty set; two concurrent sessions copy once (a second backend in the same style as the first-admin race test).

**End-to-end** (`wood.spec.ts`, desktop and phone). The fake Supabase server learns the two tables, the function and failure switches, and computes the snapshot with `@gb/dsp` so its values match the database's. Scenarios:
- defaults and results;
- the validation message and hidden results;
- real-time recalculation (357.1 kg/m³);
- reset;
- save, load, update and deselect;
- delete, confirmed and cancelled, and deleting the loaded panel;
- library order;
- the empty state and "Load Default Panels" with 5 reference panels, an empty set and a failure;
- the library load failure;
- a panel deleted elsewhere;
- an administrator seeing only their own panels;
- detecting a frequency through the dialog with the WAV fixture of `tap-tone-dialog` ("181.6" in the field, the spectrum reopening after save and load);
- the PDF download name and `%PDF` header;
- French labels.

## Risks / Trade-offs

- **[Formulas in two languages]** The SQL functions and the TypeScript module could drift. Both are tested against the spec's examples and the same dataset plates; a formula change must touch both and their shared tests.
- **[Generated columns keep old values after a function change]** Replacing a formula function does not recompute stored rows. The formulas are fixed by the spec; a future change would rewrite the columns in its migration.
- **[pdf-lib is not actively developed]** It is small, MIT-licensed and has no known advisories. If that changes, only `renderReport` moves to another library.
- **[Font files add about 600 KB]** They are fetched only when a PDF is generated, and cached by the browser.
- **[Number inputs and locales]** Chrome and Firefox accept the locale's decimal separator differently. Both report unparsable text as empty, which the spec treats as missing, so the worst case is a validation message, never a wrong number.
- **[The defaults give an implausible E_C]** 280 × 70 × 3 mm at 90 Hz gives E_C ≈ 0.01 GPa. The spec keeps these defaults (legacy finding, open question 2).

## Migration Plan

**Deploy:**
- One additive migration, after the `tap-tone-dialog` migration that defines `spectrum_record_is_valid`.
- No environment variables are added.
- The font files ship with the app build.

**Rollback:**
- Redeploy the previous app build.
- The tables can stay, because nothing else reads them yet.

**Legacy import:** `legacy-data-migration` will insert panels as `service_role` with the ten inputs and the mapped spectra. The generated columns produce the corrected results, and the report compares them with the legacy snapshot.

## Open Questions

These change no part of the approach or the tasks:
- **The dataset's target thickness and mass.** Which plate settings did the dataset's author use? Only if the owner wants those columns as fixtures too.
- **Linking panels to builds** ("Still open" 1 in `docs/rewrite/README.md`). If yes, a nullable `build_id … on delete set null` is an additive migration, and it gives `guitar-builds`' "Linked wood panel survives" scenario something to act on. Today no panel references a build.
- **Realistic default inputs, "save as copy" and an unsaved-changes warning** (legacy findings, questions 2 and 7). These are spec changes the owner may want later.
