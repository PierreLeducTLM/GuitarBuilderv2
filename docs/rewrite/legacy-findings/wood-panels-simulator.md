# Findings: wood-panel-properties and guitar-simulator

## Dead or unwired code
- `MesuredElasticityDataset.json` (repo root) is referenced nowhere (no import, fetch or migration; it only appears in the git index). It holds "Measured elastic constants and thickness targets" for 28 whole-plate samples in 4 groups: `top_woods` (Engelmann Spruce, 10), `port_orford_cedar` (2), `western_red_cedar` (8) and `back_woods` (East Indian Rosewood, 8). Each sample has id, species, length/width/thickness (mm), mass (g), density (kg/m³), f_long/f_cross/f_diag (Hz), e_long/e_cross/g_lc (GPa), `e_long_cross_gpa` (actually the E_L/E_C ratio, not GPa), target_thickness_mm and mass_target_g. Its density, E_L, E_C and G_LC values match Gore's formulas exactly, with E_C using W^4 (see Bugs #1). Worth keeping as test fixtures for the rewrite.
- Wood panels have a build reference (`build_id`, src/lib/supabase.ts:52; supabase/migrations/20251119000002_create_wood_panels_and_defaults.sql:42) that nothing in the UI ever sets or reads (src/components/WoodPropertiesCalculator.tsx:179-198). Panels cannot be linked to a build. Not specced.
- Simulator parameters that are declared but ignored by the model: `topDamping`, `backDamping`, `sidesDamping` (the hard-coded Q values are used instead), `airCouplingCoefficient`, `sideCouplingCoefficient`, `excitationAmplitude` (a fixed 0.4 N is used), `superimposedSources`, `soundHoleDiameter` (src/types/guitarSimulator.ts:8-42, 131-170; src/utils/guitarSimulator.ts:15-21). Only the 12 UI parameters drive the model.
- "Superimposed sources" overlay: state and drawing code exist but there is no toggle, and the contribution is always -200 dB ("Not implemented") (src/components/GuitarSimulator.tsx:36-42, 173-196; src/utils/guitarSimulator.ts:312).
- Peak Q factor is computed and never displayed (src/utils/guitarSimulator.ts:351-366). `calculateNaturalFrequencies` also returns a fake `coupled2DOF` (just copies the uncoupled values), a `description` and `fSides`, none of which are used (src/utils/guitarSimulator.ts:387-410). The `Coupled2DOFFrequencies`, `SensitivityAnalysisResult` and `velocity`/`phase` types are unused (src/types/guitarSimulator.ts:57-126). The `format` prop of `ParameterInput` is never passed (src/components/GuitarSimulator.tsx:648, 675).
- Unreachable UI branches: the "Enter valid measurements to calculate properties" empty state (results are null only when there are errors) (src/components/WoodPropertiesCalculator.tsx:791-793). The "Please enter a name" warning toast never shows in practice, because the Save button is disabled without a name and hidden without results (src/components/WoodPropertiesCalculator.tsx:171-174, 772). The analysis `error` stream branch is also unreachable, because the stream helper throws instead (src/components/WoodPropertiesCalculator.tsx:339-341; src/services/chatService.ts:108-119).

## Bugs and inconsistencies
1. **Cross-grain modulus formula is wrong in general.** The code uses `E_C = 0.94146*rho*L^4*f_C^2/h^2 / 42`, with a comment calling 42 "empirically determined" (src/utils/woodPropertiesCalculation.ts:133-160). In fact 42 ≈ (L/W)^4 for the 605x238 mm plates in the dataset ((605/238)^4 = 41.8). Gore's formula `E_C = 0.94146*rho*W^4*f_C^2/h^2` reproduces all 28 dataset E_C values exactly, while the app formula is only right when L/W ≈ 2.55. Examples: Port Orford samples give 0.28 instead of 0.57 GPa, and the default 280x70 sample has (L/W)^4 = 256, so E_C comes out about 6x too high. **Specced the W^4 formula.** Target thickness and estimated mass change slightly as a result. The stored snapshots of existing panels were computed with the old formula.
2. The default calculator inputs are physically implausible: a 280x70x3 mm strip with f_C = 90 Hz gives E_C ≈ 0.009 GPa (Gore) or 0.053 GPa (current code), against about 0.4-1.0 GPa for real spruce (src/components/WoodPropertiesCalculator.tsx:28-39, 152-163). The defaults are specced as they are; see Open questions.
3. The analysis prompt template is read from settings (src/services/woodAnalysisService.ts:50-63), but only admins can read settings (supabase/migrations/20251119000000_create_settings_table.sql:13-21). Non-admins therefore always get the hard-coded fallback, and an admin's customised template only applies to admins. **Specced: the configured template applies to every user.**
4. Analysis error handling: `streamAsk` swallows server `error` events whose message does not start with "Stream error" (src/services/chatService.ts:108-119). `handleAnalyze` only clears loading on `done`, on an `error` event or on a throw (src/components/WoodPropertiesCalculator.tsx:333-350), so a stream that ends without `done` leaves the spinner running forever. Specced: failures show "Error" plus a message.
5. PDF: if the AI call throws, the whole PDF fails (src/components/WoodPropertiesCalculator.tsx:353-386). **Specced: the PDF still downloads, without the AI page.** The PDF also makes a second, separate LLM call even when the user has just run "Analyse".
6. The PDF uses the standard Helvetica font, which cannot render "ρ" or "³" (src/services/pdfService.ts:85), so the density line is likely garbled. All PDF text is hard-coded English (src/services/pdfService.ts:40-201). The specced localized PDF headings are therefore new work.
7. The PDF filename uses the panel name unsanitised (`/`, `:` etc.) and a UTC date from `toISOString`, while "Generated on" uses local time (src/components/WoodPropertiesCalculator.tsx:379; src/services/pdfService.ts:52).
8. Hard-coded English strings bypass i18n: input labels (src/components/WoodPropertiesCalculator.tsx:416, 437, 457, 477, 505, 535, 565, 603, 623, 650); the reset tooltip "Reset to defaults" (401), even though the key `woodCalculator.reset` exists; "Target thickness:" / "Est. Mass:" (843, 851); "Delete wood panel" (864); the capture field labels (926-929); fallback analysis errors (340, 348); all validation messages (src/utils/woodPropertiesCalculation.ts:69-98); "Close" (src/components/WoodAnalysisModal.tsx:40). The specs require EN and FR.
9. `updated_at` is never updated when a panel is updated: there is no trigger and the payload omits it (src/components/WoodPropertiesCalculator.tsx:179-205; supabase/migrations/20251119000002_create_wood_panels_and_defaults.sql:64-65). Specced a real last-update timestamp.
10. The panel name is checked trimmed but saved untrimmed (src/components/WoodPropertiesCalculator.tsx:181 vs 772).
11. Errors while fetching panels are swallowed (src/components/WoodPropertiesCalculator.tsx:135-138). The user then sees the empty state and "Load Default Panels", which silently does nothing if they actually have panels. `initializeUserData` gives no feedback on error or when the defaults are empty (src/contexts/AuthContext.tsx:57-129).
12. Spectrum map keys disagree: the migration comment says `longitudinal, cross_grain, diagonal` (supabase/migrations/20260104000000_add_fft_data_to_wood_panels.sql:5), but the stored keys are `freqLongitudinal`, `freqCrossGrain` and `freqDiagonal` (src/components/WoodPropertiesCalculator.tsx:314-317). Data migration must map the latter.
13. Stale spectra: accepting a capture without a spectrum, or typing a frequency by hand, keeps the previous spectrum for that field (src/components/WoodPropertiesCalculator.tsx:288-319). Spectra are also trimmed to 2000 Hz twice, which is harmless (src/components/FrequencyDetectionModal.tsx:798-822 and src/components/WoodPropertiesCalculator.tsx:293-312).
14. Loading another panel, deselecting or resetting discards unsaved edits without warning (src/components/WoodPropertiesCalculator.tsx:151-168, 230-253). There is no way to "save as new" from a loaded panel, because deselecting resets the inputs.
15. "Analyse" and "PDF" use the current (possibly edited, unsaved) inputs together with the saved panel's name (src/components/WoodPropertiesCalculator.tsx:322-387).
16. Simulator: the default top area (380 cm²) and back area (320 cm²) are below the slider minimum of 500 cm² (src/components/GuitarSimulator.tsx:436-451 vs src/types/guitarSimulator.ts:135, 142). **Specced a 200-2000 cm² range for the top and back** (matching the sides).
17. Simulator numeric fields are not validated: an empty field gives 0, which divides by zero and produces NaN curves; out-of-range typed values are accepted (src/components/GuitarSimulator.tsx:672); imported files are merged unchecked (315). **Specced clamping to the ranges and ignoring empty entries.**
18. Presets: Gibson J45 (top stiffness 600 N/mm, top mass 180 g) and Fleta 297 (450 N/mm, 120 g) push the top resonance above 240 Hz (J45 peaks 87.5 / 289.5 / 325.0 Hz; Fleta 96.0 / 294.5 / 336.5 Hz). Classification uses fixed bands (<120 air, <240 top, else back; src/utils/guitarSimulator.ts:378-382), so "Top Monopole" shows "—" for both presets and the real top mode is labelled "back". The preset values look arbitrary (src/types/guitarSimulator.ts:175-194). Specced as found; see Open questions.
19. The simulator's "Uncoupled modes" readouts use `sqrt(K/m)` without the air-spring term that the model includes in ω_t and ω_b (src/utils/guitarSimulator.ts:391-392 vs 299-300). The comments on the default damping values claim R is derived from the coupled frequency, but the code uses the uncoupled ω including the air spring (src/types/guitarSimulator.ts:133-151 vs src/utils/guitarSimulator.ts:305-308).
20. The simulator plot axis is 0-500 Hz but the model is only evaluated from 60 Hz, so the 0-60 Hz band is always empty (src/utils/guitarSimulator.ts:224-225, 322; src/components/GuitarSimulator.tsx:121).
21. Importing the same parameter file twice in a row does nothing, because the file input is never reset (src/components/GuitarSimulator.tsx:348-357). Parse errors use a blocking `alert` (317).
22. The physics port (src/utils/guitarSimulator.ts:282-417) is a transcription of the "Iulius Guitars" JS of Gore's 4-DOF model and has no tests. The determinant and numerators are specced verbatim. Reference outputs for verifying the rewrite: with the default parameters, peaks at 96.5 / 182.0 / 300.5 Hz, max 92.9 dB, uncoupled 114.2 / 153.8 / 275.7 Hz; with K_t = 100 N/mm, peaks at 101.0 / 208.5 / 300.5 Hz.

## Security and data-integrity concerns
- Admins hold INSERT, UPDATE and DELETE on every user's wood panels (`is_admin()`) (supabase/migrations/20251119000002_create_wood_panels_and_defaults.sql:113-123), plus SELECT on all rows re-added via `is_admin_safe()` (supabase/migrations/20251121170000_fix_user_profiles_visibility.sql:95-106). No UI needs the write access, and the INSERT check lets an admin create panels owned by anyone. The spec gives admins read-only access.
- `user_id` on wood panels is nullable (supabase/migrations/20251119000002_create_wood_panels_and_defaults.sql:41), so ownerless rows are invisible to their creator. Nothing at the database level enforces that numeric fields are > 0 (validation is client-only). Names have no length limit and `fft_data` has no size limit (it is trimmed only client-side).
- A personal email address is hard-coded as the source of reference panels in a migration and in the admin UI (supabase/migrations/20251119000002_create_wood_panels_and_defaults.sql:212-277; src/components/AdminPanel.tsx:235-254).
- "Load Default Panels" copies the reference panels client-side after a count check and the button is not disabled while it runs, so a double click can duplicate them (src/contexts/AuthContext.tsx:61-116; src/components/WoodPropertiesCalculator.tsx:812-821).
- Settings has no DELETE policy, and SELECT is admin-only (see Bugs #3). Making the template readable by all users requires a read path for that one key only. Do not expose the whole settings table.

## Open questions for the owner

2. Should the default inputs be replaced with realistic whole-plate values (e.g. dataset sample 1: 605x238x4.0 mm, 228 g, 61.6/105/38.2 Hz)?
3. Should a panel be linkable to a build (the unused build reference), or should wood panels feed the simulator (e.g. top mass from the estimated panel mass)?
4. PDF: degrade without the AI page (specced) or fail? Reuse the last "Analyse" result instead of making a second LLM call? Include the stored tap-tone spectra as graphs?
5. Should "Analyse" and "PDF" also work on unsaved calculations? Should they use the saved values rather than the current edits?
6. Should the analysis question and properties block follow the UI language (currently always English)?
7. Do you want a "save as copy" action and an unsaved-changes warning when switching panels?
8. Simulator: classify peaks by mode order (1st = air, 2nd = top, 3rd = back, as the T(1,1)₁/₂/₃ labels suggest) instead of fixed 120/240 Hz bands? Are the J45 and Fleta preset values correct? Are the area range (200-2000 cm²) and the clamping behaviour acceptable?
9. Should simulator configurations be saved per user? Today nothing is persisted, although supabase/migrations/20251121000001_fix_admin_rls_policies.sql:102 mentions "Simulator data".
10. Should admins curate reference panels directly rather than by "syncing" a hard-coded account's library (admin-console)?
