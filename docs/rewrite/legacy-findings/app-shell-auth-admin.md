# Findings: application shell, authentication, roles, admin console

Capabilities written: `openspec/specs/app-shell`, `openspec/specs/user-auth`, `openspec/specs/admin-console`.

## Dead or unwired code
- `src/utils/adminHelpers.ts:1-212`: never imported anywhere. It would have provided: system stats that also count messages and embeddings (`:20-50`); per-user counts of builds/references/conversations (`fetchUserStats`, `:131-157`); cross-user lists of builds, references and conversations joined to the owner's email (`:162-211`); direct role update (`:73-88`) and user deletion through the auth admin API (`:94-104`). The direct update and admin-API delete would fail under current server rules (no admin UPDATE policy on profiles; the admin API needs a service key), and the email joins have no foreign key to profiles. The live console has no per-user counts or cross-user browsing. Owner decides whether to build those.
- `src/contexts/AuthContext.tsx:50-54,224`: `refreshProfile` is exposed but never called. So a role change only reaches the affected user on their next session event or reload.
- `src/contexts/AuthContext.tsx:57-130`: `initializeUserData` is misnamed. It is not called at sign-up; only the "Load default panels" button uses it (`src/components/WoodPropertiesCalculator.tsx:815`). That button is live and the wood-panel agent owns it.
- `src/components/AdminPanel.tsx:177-182`: the deletion summary returned by the server is only written to the console and never shown.
- Settings `description` (`supabase/migrations/20251119000000_create_settings_table.sql:5`) is written (`AdminPanel.tsx:209`) but never displayed.
- `is_admin()` is kept only as an alias of `is_admin_safe()` (`20251121170006_cleanup_duplicates.sql:15-23`), so two functions do the same job.
- `20251118000000_add_user_profiles_and_admin_roles.sql:260-280`: admin policies for `wood_tops`. That table was later renamed to `wood_panels` and these policies were dropped (`20251119000002...sql:25-32`).
- Unused translation keys: `app.loading` (`main.tsx:32` hard-codes "Loading..."); `language.en`/`language.fr` (`LanguageSwitcher.tsx:21,31` hard-code "EN"/"FR").
- Developer artifacts: `ADMIN_PANEL_FIX_SUMMARY.md`, `check_trigger_status.sql`, and the debug, backfill and diagnostic migrations `20251121170005`, `20251121172300` and `20251121172900` (they insert orphan profiles and print NOTICEs).
- `src/i18n.ts:12` has `debug: true` in production, and `AuthContext.tsx:58-125` emits `[AuthDebug]` console logs that include user IDs.

## Bugs and inconsistencies
- **Default panels at sign-up.** The admin UI says defaults "will be automatically copied to every new user account upon signup" (`AdminPanel.tsx:613`, `admin.note5`, section title `admin.defaultWoodPanels` "...for New Users"). The latest trigger only creates the profile (`20251121173500_finalize_trigger_function.sql:10-40`). Copying was removed on purpose in `20251121145000_fix_defaults_logic.sql:8-30` in favour of a manual "Load default panels" button. Specced: new accounts start empty, defaults load on demand, and the admin text is corrected.
- **Prompt template ignored for non-admins.** Only admins can read settings (`20251119000000:13-21`). Every user's wood analysis reads the template (`src/services/woodAnalysisService.ts:49-62`), so non-admins silently fall back to the hard-coded default. Specced: the saved template applies to all users.
- **Admin deep links redirect.** `AuthContext.tsx:167-186` sets `loading=false` on the initial auth event before the profile arrives. Admin routes are only registered when `isAdmin` is true (`App.tsx:583-588`), and the wildcard route sends the user to `/builds` (`App.tsx:589`). So reloading `/admin` or `/references` as an admin most likely ends on `/builds`. Specced: wait for the role before redirecting.
- **Admins see everyone's data in regular sections.** `20251121000001_fix_admin_rls_policies.sql` removed admin SELECT on builds, conversations, messages, FFT results and wood panels so admins would see only their own data. `20251121170000_fix_user_profiles_visibility.sql:58-106` added those policies back. Its comment (`:112-115`) claims "user-specific policies are evaluated first", but that is false: permissive policies are OR'ed. The Builds list (`App.tsx:277-280`) and the chat list (`src/services/chatService.ts:26-31`) do not filter by owner, so admins see all users' builds and conversations. Wood panels do filter (`WoodPropertiesCalculator.tsx:128-132`). Specced: admins see only their own data in regular sections; cross-user reads are for the console.
- **Theme outside the shell.** The theme provider only wraps the shell (`App.tsx:355,593`). The sign-in screen, the loading screen and the public story page (`main.tsx:19-38`) never apply the stored theme on a fresh load; on a normal first load they render light. Specced: the theme applies on all screens.
- **System theme does not follow live changes.** "System" is resolved once and never updates when the OS setting changes (`ThemeContext.tsx:32-47`, no change listener). Specced: follow live changes.
- **No preferences on mobile.** The mobile slide-out menu has no theme selector or language switcher (`App.tsx:366-430`; they exist only in the desktop header at `App.tsx:450-452`). The sign-in screen has neither. Specced: reachable on all viewports.
- **Password hint in the wrong mode.** "Minimum 6 characters" shows only in sign-in mode (`Auth.tsx:139-141`). Specced: shown in sign-up mode. The 6-character check also runs at sign-in (`Auth.tsx:29`); that is harmless and kept.
- **Sign-up message may not match config.** The sign-up success text always says "check your email to verify" (`Auth.tsx:47`). The local config has `enable_confirmations = false` (`supabase/config.toml:94`), so the user is signed in at once and the message barely shows. Specced both paths.
- **Hard-coded English (not localized):** `main.tsx:32`; `App.tsx:85`; `AdminPanel.tsx:121,129,159,243,254,324,331,488,515,527,613-614,637`; the raw role value in the badge (`AdminPanel.tsx:499`); dates formatted in the browser locale rather than the app language (`AdminPanel.tsx:503`). Auth and server error messages are shown verbatim in English (`Auth.tsx:45,55`; `AdminPanel.tsx:152,191,219,298`).
- **French translations.** FR has 303 of 305 EN keys. Missing: `builds.tabOverview` and `builds.tabSequence` (these fall back to EN).
- **Inconsistent confirmation.** Sync uses the native browser `confirm()` (`AdminPanel.tsx:227`) while every other confirmation uses the app dialog. Specced: the app dialog.
- **Sync is not atomic.** It deletes all defaults, then inserts (`AdminPanel.tsx:258-289`). A failed insert leaves zero defaults. Specced: all-or-nothing.
- **Sync drops FFT data.** Sync omits the newer `fft_data` column of wood panels (`20260104000000_add_fft_data_to_wood_panels.sql:2` vs the field list at `AdminPanel.tsx:266-283`). The sign-up copy (`AuthContext.tsx:93-111`) omits it too. Specced the fields that are copied today; the owner should decide about FFT data.
- **Orphan accounts are invisible.** "Total Users" and the user list count profiles, not accounts (`AdminPanel.tsx:74`, `get_all_user_profiles`). An account whose profile creation failed does not appear and cannot be deleted from the UI.
- **Inconsistent admin checks.** `admin_delete_user` checks admin by querying profiles directly (`20251121220500_update_admin_delete_user.sql:28-33`) rather than through `is_admin_safe()` like the other RPCs. It works because the function is SECURITY DEFINER, but it is inconsistent. The comment in `20251121220000:56` saying wood panels are "not cascaded" is wrong (`20251119000002:41`).
- **Backfills assign 'user' without checking for an admin.** `20251121172300:9-17` and `20251121172900:9-18` give every backfilled profile the role 'user' without checking whether an admin exists. `20251121170005:56-70` handles first-admin correctly.
- **Unreachable access-denied view.** The console's own "Access Denied" view (`AdminPanel.tsx:338-348`) cannot be reached in practice because the route is not registered for non-admins.
- **No Escape key.** Neither the confirmation dialog nor the text-input dialog closes on Escape (`ConfirmModal.tsx`, `InputModal.tsx`). Not specced.

## Security and data-integrity concerns
- **Self-promotion to admin.** The profile INSERT policy only checks `auth.uid() = id`, not the role (`20251121172300_fix_trigger_insert_policy.sql:47-53`). The trigger swallows profile-creation errors (`20251121173500:32-38`). A user whose profile is missing can therefore insert their own profile with `role='admin'`. Recommend server-only profile creation with the role forced to 'user'.
- **First-admin race and open sign-up.** The first-admin rule is COUNT-then-INSERT with no lock (`20251121173500:19-29`), so two simultaneous first sign-ups can both become admin. With open sign-up (`config.toml:85,89`), whoever registers first on a fresh deployment becomes admin. Recommend explicit admin bootstrapping.
- **Owner email hard-coded.** `pierre@leduc.tech` appears in client code (`AdminPanel.tsx:236-254`), in EN and FR translations (`admin.syncDefaults`, `admin.clickToSync`, `admin.confirmSync`) and in a migration (`20251119000002...sql:215-230`). Specced as an operator-designated source account.
- **Deletion bypasses the auth service.** `admin_delete_user` deletes rows from the auth users table directly inside a SECURITY DEFINER function whose search_path includes `auth` (`20251121220500:13-55`). It has no explicit GRANT/REVOKE, so any role can call it and only the internal check protects it. It also bypasses the auth service's own cleanup. Uploaded step photos in the publicly readable storage bucket (`20251206000000_add_step_photos_bucket.sql:12-17`) are not deleted and become orphaned files.
- **Deleting a user deletes shared references.** Their reference documents cascade (`20251006000000_add_authentication.sql:23`) and disappear from the shared library for everyone.
- **Broad admin write access.** Admin INSERT, UPDATE and DELETE policies on builds, conversations, messages, embeddings and FFT results (`20251118000000:163-258`) and on wood panels (`20251119000002:113-123`) were never removed. Admins can modify or delete any user's data through the API. Specced as current behaviour ("full access", per `admin.note1`); the owner should confirm.
- **Role model gap for references.** The References section is admin-only in the UI (`App.tsx:340-347,583-588`), but any signed-in user may insert reference documents and edit or delete their own (`20251121000000_share_references_across_users.sql:40-73`). A non-admin could add to the shared knowledge base by calling the API directly.
- **Profile email can be spoofed.** Users can update their own profile row (`20251118000000:60-66`). The role is pinned, but the denormalized `email` is not, so a user can change the email the admin list shows. Nothing syncs the profile email when the account email changes.
- **Settings.** Admins may insert any key (`20251119000000:33-41`); there is no delete policy. Low risk.
- **Anonymous grant.** `is_admin_safe()` is granted to `anon` (`20251121170002:33`). Harmless.
- **Auth URLs point to localhost.** The verification-email site URL is localhost only (`config.toml:74-76`). Production must configure it on the hosted project.

## Open questions for the owner
- Should admins see only their own data in Builds and Chat (specced, matching the stated intent of `20251121000001` and `20251121170000`'s comment), or everyone's (current actual behaviour)?
- Should default wood panels be copied automatically at sign-up (admin UI text) or loaded on demand (latest migration; specced)?
- Which account should Sync use as its source: a fixed operator-configured account (specced), the current admin's own panels, or should defaults be edited directly? Should FFT data be included?
- On a first visit, should the app detect the browser language? Currently the order is localStorage, cookie, then `<html lang="en">` (`src/i18n.ts:14`), so it is effectively always English; specced as is.
- Should auth and server error messages be translated into French instead of shown raw?
- Should email verification be required in production? The hosted setting is unknown; locally it is off.
- Password reset, email change and self-service account deletion do not exist. Are they wanted?
- When a user is deleted, should their shared reference documents move to the deleting admin instead of being deleted?
- Should the console show per-user resource counts (only the dead `adminHelpers.fetchUserStats` does), and should it show the deletion summary?
- Should an empty prompt template be rejected? Currently it can be saved and would send an empty analysis question.
- Is it acceptable that role changes reach the affected user only on their next reload or sign-in?
