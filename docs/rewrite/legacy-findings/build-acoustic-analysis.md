There are no frequency bands and no classification. `fft_results.air_resonance` / `body_resonance` (supabase/migrations/20251001132337_create_fft_results_table.sql:37-38) are always inserted as `null` (BD:72-73) and never read. The spec keeps them as optional empty fields so existing data can be migrated.
- The window function is generated but never applied: `windowRef` (EFA:134, EFA:159-162). `applyWindow` (fftUtils.ts:102-114) is imported but unused (EFA:37). See bug 1.
- Unused utilities: `resampleAudioBuffer` (audioFileLoader.ts:108-129); `extractTimeDomainData` (audioFileLoader.ts:134-156, imported but unused at EFA:61); `calculateQFactorsForPeaks` (qFactorCalculation.ts:167-184); `calculateQFactorAlternative` (a -6 dB / ±100 Hz Q variant, qFactorCalculation.ts:190-200); `frequencyToBin` imported but unused in EFA (EFA:40).
- Unused config fields (stored, imported and exported, but with no effect): `amplitudeScale` (fftConfig.ts:23,111; there is no linear/log amplitude toggle); `sampleRate` 48000 "for file input" (fftConfig.ts:30,116; EFA:923-927 is an empty "would resample here" block); `logDecrementCaptureDuration` 5 s (fftConfig.ts:42,122).

- Index `idx_fft_results_created_at` (20251001132337:63) is never used; the list is ordered by `order_position`.

## Bugs and inconsistencies
1. **The window setting has no effect.** The browser analyser always applies its own Blackman window (live EFA:188-191, file EFA:950-952). Specced: the selected window is applied.
2. **The dB scale is a double log.** The code reads the analyser's 8-bit "byte" spectrum, which is already in dB and linearly maps -100..-30 dBFS onto 0..255. It then treats byte/255 as a linear amplitude and takes 20*log10 of it again (EFA:276, 282-284, 963-969). Stored and displayed values are A = 20*log10(B/255), with B = floor(255*(Y+100)/70) clipped to 0..255, where Y is smoothed dB (1/N normalisation, Blackman window). So 0 dB means Y >= -30 dBFS and -200 dB means Y <= -100 dBFS. Specced: coherent-gain-normalised dBFS (a full-scale sine reads 0 dB). **Migrating legacy saved spectra:** Y ≈ -100 + 70*10^(A/20) (±0.27 dB quantisation). For the new scale, add ≈ +13.56 dB (the Blackman coherent gain of 0.42 plus the single-sided factor of 2). Points that were released in the dB domain (not at max) are only approximately invertible.
3. **The peak threshold multiplies dB values** (peakDetection.ts:35-36): threshold = max_dB * sensitivity. With negative dB values the threshold sits above the maximum, so no peaks are found unless the spectrum reaches 0 dB. Sensitivity 0 then rejects everything below 0 dB, which inverts the meaning. Specced: a linear relative threshold, A >= A_max + 20*log10(s).
4. **Standard peak detection scans the whole spectrum (0..Nyquist)**, not the selected range (EFA:372-380, 976-984). Peaks outside the range are drawn off-canvas and still take places in the top 10. In resonance mode the threshold maximum also comes from the full spectrum (peakDetection.ts:169-182). Specced: detection is restricted to the range.
5. **A loaded file is analysed only over its last N samples.** The offline analyser is read once after rendering finishes (EFA:941-963), so a tap early in a file is lost. Specced: whole-file peak-hold over 50%-overlapped frames.
6. **The first file load likely fails.** The unmount-cleanup effect depends on `stopRecording`, which is re-created whenever `inputSource` changes (EFA:260, 1272-1282). `setInputSource('file')` (EFA:911) therefore runs the cleanup, which closes and nulls the AudioContext just created for decoding (EFA:251-255). `processAudioFile` then returns early (EFA:939) and Play does nothing (EFA:1038). A second load works. Not confirmed in a browser.
7. **The displayed "file sample rate" is the decoding context's rate.** `decodeAudioData` resamples to the context rate (audioFileLoader.ts:51; context created at EFA:915 or 48 kHz from the mic). Specced: analyse at the file's own rate.
8. **Q-factor can be computed from the search-window edge.** When the threshold is never crossed, `lowerBin`/`upperBin` end at the ±50 Hz window edge and pass the "found" check (qFactorCalculation.ts:96-131). Specced: no Q in that case.
9. **Logarithmic decrement reports frequency at 2x the true value.** It uses consecutive zero crossings, which are half a period apart (logarithmicDecrement.ts:74-75). This halves tau. Specced: f = 1/(2*lobe duration).
10. **The decay envelope mixes units.** It uses the per-cycle delta as a per-second rate, exp(-delta*t) (logarithmicDecrement.ts:187-196). Specced: exp(-delta*f_avg*t).
11. **The time-domain view is mostly empty.** Data is captured only when log decrement is enabled, only from the mic, and only as the last N samples, about 0.34 s at the defaults (EFA:297-300). It is never set for files. Specced: the latest frame (mic) or the whole file.
12. **Resonance mode cannot record repeated taps of the same resonance.** A tap needs a frequency more than 5 Hz away from the last recorded one (EFA:329-330). That contradicts "Record 3-4 peaks for best results" and the averaging. Specced instead: re-arm once the response falls to -40 dB or below, plus the 1 s cooldown. Note that with averaging window size 1 (pure hold) it never re-arms.
13. **The tap counter and limit disagree.** The counter shows "n / 4" (EFA:1839) but the hard limit is 10 (EFA:335).
14. **Save and export in resonance mode use the live held spectrum**, not the averaged spectrum that is on screen (EFA:992-1010, 1073-1134 vs 450). Specced: save what is displayed.
15. **Most settings are frozen while capturing.** The animation loop is started once from `startRecording` (EFA:218) and keeps its first closure. Config, `selectedPeak` and overlay changes during capture are ignored, including the live Q update at EFA:385-400. FFT size and smoothing apply only at the next Start (EFA:223).
16. **Hovering after Stop erases the held spectrum.** `renderSpectrum` draws it only when `isRecording` or the source is a file (EFA:679; triggered at EFA:1740-1744). Selected overlays are not redrawn when the selection changes while idle; `renderSpectrum` is only called on mouse move, reset and file load. Specced: overlays appear immediately.
17. **No input validation.** Frequency and display ranges (EFA:1463-1531), averaging size (EFA:1540-1552), Q level (EFA:1593-1603) and minimum cycles (EFA:1627-1638) are unchecked; min == max divides by zero. Imported config is not type-checked (EFA:1153). A corrupt stored config makes `JSON.parse` throw at init and crashes the build page (EFA:87-88). Specced: reject invalid values. The bounds are my choice.
18. **Off-by-one at Nyquist.** `getBinRange` caps at N/2, but the arrays hold N/2 bins (fftUtils.ts:186-189). When the range max is >= fs/2, save and export emit one point with an undefined amplitude (EFA:1003-1007, 1084-1087, 1121-1124).
19. **Failures give no feedback.** A failed log decrement shows nothing (EFA:1250-1259), and a Q that cannot be computed just hides the panel (EFA:1778, 1986). Specced: tell the user.
20. **"Averaging Window Size" is not an average.** It is labelled "Number of spectra to average" (EFA:1553-1555) but actually sets the release factor of a peak-hold (EFA:286-294). Specced as peak-hold with release.
21. **Reorder errors are silent.** `Promise.all` over update calls never rejects on database errors, so the `fetchFFTResults` fallback never runs (BD:156-169). Drag-and-drop reordering does not work on touch devices (BD:301-316), even though the code mentions Android/mobile (EFA:179-180, 196-197).
22. **Localisation is missing.** All analyzer UI text is hard-coded English (EFA:1284-2123); only `analyzer.micError` is translated (EFA:221). Saved-result dates are always formatted en-US (BD:179-185). The window descriptions are English (fftUtils.ts:165-174).
23. **A click can select a hidden peak.** Clicking the plot picks the nearest of all detected peaks, including ones beyond the top 10 or outside the range (EFA:1748-1764). Selection is matched by exact frequency, so the highlight is lost when live peaks shift (EFA:584, 861).

## Security and data-integrity concerns
- **Saved FFT results are publicly readable and writable.** The original "Anyone can read/insert/update/delete FFT results" policies (20251001132337_create_fft_results_table.sql:45-60) were never dropped. `20251006000000_add_authentication.sql` dropped the public policies of other tables (lines 35-53) but only added owner policies for `fft_results` (192-238). Policies are permissive and OR-ed, so anyone holding the public client key, unauthenticated included, can read, insert (into any build), modify and delete every user's saved FFT results. Specced: owner and admin only.
- Admins have insert/update/delete on every user's FFT results (20251118000000_add_user_profiles_and_admin_roles.sql:248-258, never dropped). Admin SELECT was dropped (20251121000001_fix_admin_rls_policies.sql:61) and then re-added (20251121170000_fix_user_profiles_visibility.sql:88-92). Confirm whether admin write access is intended.
- `frequency_data` is unbounded JSON with no shape check (20251001132337:36). Combined with the public insert policy, this allows storage abuse and malformed rows that break overlay drawing.

## Open questions for the owner
- Peak "sensitivity": I specced a relative threshold where higher means stricter (0.5 keeps peaks within 6 dB of the strongest). Would you prefer an inverted control where higher means more peaks?
- Whole-file analysis: I specced peak-hold over 50%-overlapped frames. Would an average (Welch) be better?
- Air/body resonance: should the system auto-identify them, and in which frequency bands, and store them (frequency, amplitude, Q)? Or should the empty fields be dropped?
- Log decrement: should there be a dedicated decay capture (the unused 5 s config suggests one) and a band-pass around the selected peak before zero-crossing analysis? The current method works on the raw multi-mode signal.
- Damping ratio: keep the small-damping approximation zeta = delta/(2*pi), or use the exact delta/sqrt(4*pi^2 + delta^2)?
- Taps: is the target 4 or the cap 10? Is my re-arm rule acceptable?
- Legacy saved spectra use the old double-log dB scale (bug 2). Convert them on migration or keep them as-is?
- Should a saved result also store its analysis context (sample rate, FFT size, window, mode) so overlays can be interpreted? Should overlays have a legend naming each result?
- Should saved results be renamable? The update policy exists but there is no UI.
- Frequency range validation bounds (0 <= min < max <= fs/2) and bandwidth level < 0 are my choices.
